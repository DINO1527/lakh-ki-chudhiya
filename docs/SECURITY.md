# Security and privacy checklist

- Anonymous users read published product/content only. Customers access their own profile, address, cart, orders and review eligibility. Guest order access requires an unguessable expiring authorization mechanism, not readable order reference. Staff get explicit server-checked permissions; owner handles sensitive settings. Never trust editable user metadata for roles.
- Enable RLS on exposed tables, least-privilege grants, explicit policies for SELECT/INSERT/UPDATE/DELETE, safe views/functions. Test anon, customer A/B and permitted/denied staff. Elevated service/secret keys never in browser or logs; prefer user-scoped client. Carefully review SECURITY DEFINER functions, fixed search_path, schema qualification and execute grants. Auth checks at every mutation/read boundary, not middleware/layout alone.
- Zod server validation, size/count/file bounds, server-side totals and idempotency including replay mismatch. Atomic PostgreSQL transactions, row locks/constraints for stock, status and eligibility. Rate-limit checkout/auth/reviews/uploads with low-cost compatible approach. Verify origin/CSRF defenses for cookie-authenticated mutations, restrict redirects, no open redirects, render reviews as safe text; no untrusted HTML.
- Product media uses the private Supabase Storage `product-media` bucket. Anonymous users can request signed URLs only for published media attached to published products; public object listing and draft signing are denied by `storage.objects` RLS. After the Stage 2 migration, admin Storage mutations require an active owner/staff row in `public.staff_members`, checked through a fixed-search-path security-definer function. Never use editable JWT metadata for privilege checks. Validate MIME/signatures, size, allowed types and random keys; block unsafe SVG, HTML and executable uploads; no arbitrary URL fetching. Publish only approved assets; archive media metadata to revoke public signing and retain its history. Strip sensitive metadata where feasible. Do not alter Supabase-managed `storage` tables directly; use the Storage API.
- Never shared-cache admin/account/order/checkout/session responses or private RSC payloads. Service worker allowlist public endpoints, exclude cookie-bearing personalized responses and mutations; clear sensitive state on logout. Test cache isolation.
- Secret management: local ignored env files, Worker secrets and development scope; rotate on leak. Avoid PII in logs, screenshots, WhatsApp text or analytics. Provide accurate policies, retention, access/deletion procedure aligned with owner's obligations. Use HTTPS and security headers, CSP compatible with actual assets, no insecure wildcard exemptions.
- Environment isolation: keep hosted UAT and live on separate Supabase projects and environment-scoped Worker secrets. Each project gets the same private Storage bucket and RLS migrations, but objects remain separate. Development and testing use UAT; disposable local Supabase may be used for destructive reset tests. UAT uses only synthetic accounts and catalogue rows; never copy production PII or apply UAT seeds to live. Verify the target project reference before every hosted migration, bucket sync or fixture write. See [ENVIRONMENTS.md](ENVIRONMENTS.md).
- Dependency/tool review: pinned versions, license, advisories, supply chain, no arbitrary third-party scripts or agent instructions; MCP least privilege and no production credentials. Security testing only local/authorized staging; no real payments or live orders.
